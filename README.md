# Rowhou8e Bar Control

ระบบควบคุมงานบาร์น้ำประจำวันสำหรับร้านโรว์เฮ้าส์ (Row House) — ออกแบบมือถือเป็นหลัก (mobile-first) สำหรับพนักงานหน้างาน และให้เจ้าของร้าน/ผู้จัดการตรวจสอบสถานะได้ทุกที่

สร้างด้วย **Next.js 14 (App Router) + TypeScript + Tailwind CSS** พร้อมสคีมาฐานข้อมูลจริงสำหรับ **Supabase (PostgreSQL)**

## 1. วิเคราะห์ Requirement และ User Flow

### สิทธิ์ผู้ใช้ 3 ระดับ

| สิทธิ์ | ดูข้อมูล | ทำเช็กลิสต์/ต้มนม/ปรับสต็อก | แก้ไขเช็กลิสต์ย้อนหลัง | อนุมัติจัดซื้อ | ตั้งค่าระบบ | สรุปการเงิน (รายงานเงินสด) |
|---|---|---|---|---|---|---|
| **Owner** | ทั้งหมด | ✓ | ✓ | ✓ | ✓ | ✓ |
| **Manager** | ทั้งหมด | ✓ | ✓ | ✓ | ✗ | ✗ (ทำได้ทุกอย่างยกเว้นส่วนนี้) |
| **Staff** | ทั้งหมด (อ่าน) | ✓ | ✗ | ✗ (เสนอได้อย่างเดียว) | ✗ | ✗ |

> อัปเดต: ทุกตำแหน่ง (รวม Staff) ส่งแจ้งเตือนขอสั่งของให้แผนกไหนก็ได้ และเพิ่มวัตถุดิบใหม่เข้าคลังกลางได้เอง (ที่หน้า "สั่งสินค้า") — การกำหนดผู้ขาย/ราคายังเป็นสิทธิ์ของ Owner/Manager เท่านั้น

### User Flow หลัก — พนักงาน (Staff)

```
เปิดแอป → เลือกชื่อ → กรอก PIN → หน้าหลัก (Dashboard)
  → เห็นบาร์/สถานีของตัวเอง (เช่น "บาร์น้ำ 2 — กาแฟ") + สถานะเช็กลิสต์วันนี้ → กด "ทำเช็กลิสต์"
  → ตรวจรายการเฉพาะของบาร์ตัวเองทีละข้อ (แต่ละบาร์มีจำนวน/รายการไม่เท่ากัน — เลือกสถานะ + หมายเหตุ/รูปถ้าผิดปกติ) → ส่ง
  → (ถ้ามีการต้มนม) กด "บันทึกการต้มนมใหม่" → กรอกข้อมูล → ระบบคำนวณวันหมดอายุอัตโนมัติ → บันทึก
  → เจอวัตถุดิบใกล้หมด/หมด → เข้าหน้าสต๊อก → ปรับจำนวน หรือสร้างรายการเสนอซื้อ
  → เช็กการแจ้งเตือนเป็นระยะจากศูนย์แจ้งเตือน (รวมถึงสรุปช่วงปิดร้านตอนเย็น)
```

พนักงานแต่ละคนถูกผูกกับ "บาร์ที่ประจำ" (`stationId`) ไว้ล่วงหน้าโดย Owner (ตั้งค่าได้ที่หน้า Settings) หน้าเช็กลิสต์จะพาไปที่ฟอร์มของบาร์ตัวเองโดยอัตโนมัติ แต่พนักงานยังสามารถเลือกทำเช็กลิสต์แทนบาร์อื่นได้จากหน้ารายการ (เช่น กรณีลาป่วย/สลับกันทำ)

### User Flow หลัก — Manager / Owner

```
เปิดแอป → ล็อกอิน → หน้าหลัก เห็นภาพรวมทั้งร้าน (สีเขียว/เหลือง/แดง/เทา)
  → เข้าหน้ารายการเสนอซื้อ → ตรวจรายการ "รออนุมัติ" → อนุมัติ/ยกเลิก
  → ติดตามสถานะจนถึง "สั่งซื้อแล้ว" → "รับสินค้าแล้ว" (ระบบเพิ่มเข้าสต๊อกอัตโนมัติ)
  → เข้าหน้าประวัติเพื่อตรวจสอบว่าใครทำอะไรเมื่อไหร่
  → (เฉพาะ Owner) เข้าหน้า Settings ปรับเวลาเช็กลิสต์ / อายุการเก็บนม / สิทธิ์พนักงาน
```

### แผนที่หน้าจอ (Sitemap)

```
/login                          เลือกชื่อ + PIN
/dashboard                      ภาพรวมวันนี้ (หน้าแรกหลังล็อกอิน) — สถานะเช็กลิสต์ของทุกบาร์แบบย่อ
/checklist                      การ์ดสถานะเช็กลิสต์วันนี้แยกตามบาร์ + ประวัติ (กรองตามบาร์ได้)
/checklist/new?station=xxx      ฟอร์มทำเช็กลิสต์ตามรายการเฉพาะของบาร์นั้น (จำนวนข้อต่างกันไปตามบาร์)
/checklist/[id]                 ดูรายละเอียดเช็กลิสต์ที่ทำไปแล้ว (ระบุชื่อบาร์)
/milk                           รายการล็อตนมต้มทั้งหมด + กรองสถานะ
/milk/new                       ฟอร์มบันทึกการต้มนมใหม่
/stock                          รายการวัตถุดิบทั้งหมด แยกหมวดหมู่
/stock/[id]                     รายละเอียด + ปรับจำนวน + แจ้งของเสีย
/purchase-requests              รายการเสนอซื้อ (tab ตามสถานะ)
/purchase-requests/new          ฟอร์มเสนอซื้อใหม่
/purchase-orders                      รวมใบสั่งซื้อ (tab ตามสถานะ) + ปุ่มดูสรุปรายเดือน
/purchase-orders/[id]                 รายละเอียดใบสั่งซื้อ - ถ้าสถานะ "ร่าง" แก้ไขราคาต่อหน่วยแต่ละรายการได้ก่อนส่งให้ผู้ขาย
/purchase-orders/report               สรุปยอดซื้อรายเดือน แยกตามหมวดหมู่/รายการสินค้า พร้อมปริ้นรายงาน
/notifications                  ศูนย์แจ้งเตือน แยกระดับความสำคัญ
/history                        ประวัติการใช้งาน ค้นหาย้อนหลังได้
/settings                       ตั้งค่าระบบ (เฉพาะ Owner)
```

## 2. โครงสร้างฐานข้อมูล (Database Schema)

ไฟล์ SQL ฉบับเต็มอยู่ที่ `src/lib/supabase/schema.sql` (โครงสร้างตาราง) และ `src/lib/supabase/rls-policies.sql` (สิทธิ์การเข้าถึง)

### ตารางหลักและความสัมพันธ์

```
stations ──┬─< employees (station_id, nullable — null = ทำได้ทุกบาร์)
           ├─< checklist_template_items (station_id — รายการเช็กลิสต์เฉพาะของแต่ละบาร์)
           └─< checklist_runs (station_id)

employees ──┬─< stock_items (updated_by)
            ├─< checklist_runs (submitted_by)
            ├─< milk_batches (boiled_by)
            ├─< purchase_requests (requested_by, approved_by)
            └─< history_logs (actor_id)

stock_categories ──< stock_items

checklist_template_items ──< checklist_entry_items >── checklist_runs

stock_items ──< purchase_requests (stock_item_id, nullable)

notifications ──< notification_reads >── employees

app_settings  (ตารางเดียว/singleton — เก็บค่าคอนฟิกทั้งร้าน รวมเวลาปิดร้านสำหรับสรุปท้ายวัน)
```

**ตารางทั้งหมด:** `stations`, `employees`, `stock_categories`, `stock_items`, `checklist_template_items`, `checklist_runs`, `checklist_entry_items`, `milk_batches`, `purchase_requests`, `notifications`, `notification_reads`, `history_logs`, `app_settings`

จุดออกแบบที่สำคัญ:

- **`stations` (บาร์น้ำ/สถานี) เป็นตารางแยก** — ร้านมีได้หลายบาร์ (ตัวอย่างมี 3 บาร์: เครื่องดื่มหลัก/กาแฟ/ปั่น-สมูทตี้) แต่ละบาร์มีรายการเช็กลิสต์ของตัวเอง (`checklist_template_items.station_id`) และทำเช็กลิสต์แยกกันเป็นรายวัน พนักงานแต่ละคน "ประจำ" บาร์ใดบาร์หนึ่งผ่าน `employees.station_id` (Owner/Manager หรือพนักงานที่ทำได้ทุกบาร์ปล่อยเป็น `null`)
- **`checklist_runs` unique ที่ `(run_date, station_id)`** ไม่ใช่ `run_date` เฉย ๆ — เพราะแต่ละบาร์ต้องทำเช็กลิสต์แยกกันในวันเดียวกันได้ (เดิมสเปกแรกออกแบบเป็นเช็กลิสต์เดียวทั้งร้าน ภายหลังปรับเป็นแยกตามบาร์ตามที่ผู้ใช้ต้องการ)
- **สรุปช่วงปิดร้าน (`closing_summary`)** ไม่ใช่ตารางใหม่ แต่เป็นแจ้งเตือนที่ระบบคำนวณสดจาก `stock_items` ทุกบาร์รวมกัน เมื่อเวลาปัจจุบันเลย `app_settings.closing_time` และมีของเหลือน้อย/หมด — ใช้เตรียมของ/สั่งซื้อล่วงหน้าก่อนเปิดร้านวันถัดไป (ดู `src/lib/derive.ts` → `generateLiveNotifications`)
- **`milk_batches` ห้ามลบ/เขียนทับ** — ทุกครั้งที่ต้มนมใหม่คือ insert แถวใหม่เสมอ (ล็อตเก่ายังอยู่ในตารางตลอด) ตรงตามสเปก "เมื่อมีการต้มนมใหม่ ให้สร้างล็อตใหม่และเก็บประวัติล็อตเก่าไว้"
- **`history_logs` เป็น append-only** — RLS อนุญาตแค่ insert/select ไม่มี policy สำหรับ update/delete เลย (ดูหัวข้อ 12)
- **สถานะ (`status`) ของ `stock_items`/`milk_batches` คำนวณจากเวลา+จำนวนจริง** ไม่ใช่ค่าที่พนักงานพิมพ์เอง เพื่อป้องกันข้อมูลไม่ตรงกับความเป็นจริง (ดู `src/lib/derive.ts` ฝั่ง client และควร reproduce ตรรกะเดียวกันด้วย Postgres function/cron ฝั่ง server สำหรับ production — ดูหัวข้อ 13)
- **`purchase_requests.auto_generated`** ใช้แยกรายการที่ระบบสร้างให้อัตโนมัติ (สต๊อกต่ำกว่าขั้นต่ำ) ออกจากที่พนักงานเสนอเอง

## 3. Wireframe ของทุกหน้า

โปรเจกต์นี้ส่งมอบเป็น **clickable prototype ที่ใช้งานได้จริง** (ไม่ใช่แค่ภาพ wireframe) เพราะฉะนั้นให้ใช้แอปจริงเป็น wireframe ที่แม่นยำที่สุด (ดูวิธีรันในหัวข้อถัดไป) ด้านล่างนี้สรุปโครงหน้าจอแต่ละหน้าเป็นข้อความ เพื่อให้เห็นภาพโดยไม่ต้องเปิดแอป:

```
┌─ Login ──────────────────┐   ┌─ Dashboard ──────────────┐   ┌─ เช็กลิสต์ (รายการ) ──────┐
│  โลโก้ Rowhou8e             │   │  สวัสดี [ชื่อเล่น] 👋      │   │  การ์ดต่อบาร์ (2-3 การ์ด): │
│  รายชื่อพนักงาน (การ์ด)   │   │  [การ์ดสถานะทุกบาร์]       │   │   - ชื่อบาร์ + สถานะวันนี้ │
│  → กดเลือกคน → คีย์แพด PIN│   │   - บาร์ 1 ✓ / บาร์ 2 ⏳   │   │   - badge "บาร์ของฉัน"    │
└───────────────────────────┘   │   - บาร์ 3 ✗ ยังไม่ทำ      │   │   - ปุ่ม "ทำเลย"           │
                                 │  [4 ตัวเลขสรุปสถานะ]      │   │  แท็บกรองประวัติตามบาร์    │
                                 │  [นมต้มที่ใช้งานอยู่]      │   │  ประวัติย้อนหลัง (list)   │
                                 │  [งานที่ยังไม่ได้ทำ]       │   └────────────────────────────┘
                                 └────────────────────────────┘

┌─ ทำเช็กลิสต์ (ฟอร์ม) ─────┐   ┌─ นมต้ม ───────────────────┐   ┌─ สต๊อก ────────────────────┐
│  หัวข้อ: ชื่อบาร์ที่ทำ     │   │  ปุ่ม "+ บันทึกต้มนมใหม่"  │   │  ช่องค้นหา                 │
│  แถบความคืบหน้า x/N        │   │  แถบกรองสถานะ (แนวนอน)     │   │  แถบกรองสถานะ + หมวดหมู่   │
│  (N ต่างกันไปตามบาร์)      │   │  รายการล็อต (การ์ด):       │   │  รายการวัตถุดิบ แยกหมวด    │
│  การ์ดต่อข้อ:              │   │   - เลขล็อต, จำนวน, สถานะ  │   │  แต่ละแถว: ชื่อ/คงเหลือ/   │
│   - ชื่อข้อ                │   │   - ต้มเมื่อ/หมดอายุเมื่อ   │   │  สถานะสี                  │
│   - ปุ่มสถานะ 6 แบบ         │   │   - ปุ่มใช้หมดแล้ว/ทิ้ง     │   └────────────────────────────┘
│   - หมายเหตุ + แนบรูป       │   └────────────────────────────┘
│  ปุ่มส่งเช็กลิสต์ (ล่างสุด) │
└────────────────────────────┘

┌─ รายละเอียดวัตถุดิบ ──────┐   ┌─ รายการเสนอซื้อ ──────────┐   ┌─ ศูนย์แจ้งเตือน ───────────┐
│  จำนวนคงเหลือ + สถานะ      │   │  ปุ่ม "+ เสนอซื้อใหม่"     │   │  สรุปตัวเลข 4 ระดับ        │
│  ขั้นต่ำ/ควรมี/วันหมดอายุ  │   │  แท็บสถานะ (แนวนอน)        │   │  แถบกรองระดับความสำคัญ     │
│  ปรับจำนวน (+/− และพิมพ์)  │   │  รายการ (การ์ด):           │   │  รายการแจ้งเตือน (การ์ด)   │
│  ปุ่มแจ้งของเสีย            │   │   - ชื่อ/จำนวน/เหตุผล      │   │   กดแล้วไปหน้าที่เกี่ยวข้อง │
│  ปุ่มสร้างรายการเสนอซื้อ    │   │   - ปุ่มอนุมัติ/สั่งซื้อ/รับ│   └────────────────────────────┘
└────────────────────────────┘   └────────────────────────────┘

┌─ ประวัติการใช้งาน ────────┐   ┌─ ตั้งค่าระบบ (Owner) ──────┐
│  ช่องค้นหา                 │   │  เวลาเช็กลิสต์ (เริ่ม/สุดท้าย)│
│  ตัวกรอง: พนักงาน/วันที่    │   │  อายุเก็บนมต้ม (วัน)        │
│  แท็บประเภทงาน (แนวนอน)    │   │  เวลาแจ้งเตือนล่วงหน้า      │
│  รายการ (ไอคอน+รายละเอียด) │   │  รายชื่อพนักงาน + สิทธิ์     │
└────────────────────────────┘   │  รายการเช็กลิสต์ (read-only)│
                                  │  รายชื่อวัตถุดิบ (read-only)│
```

## 8. วิธีเชื่อมฐานข้อมูลจริง (Supabase)

> **สถานะของโปรเจกต์นี้:** ขั้นตอนทั้งหมดด้านล่างทำเสร็จแล้วสำหรับโปรเจกต์ Supabase ที่ผูกไว้อยู่ตอนนี้ — schema/RLS/seed รันแล้ว, สร้างบัญชี Supabase Auth และผูกกับพนักงานแล้ว, และหน้าจอ UI ทุกหน้าต่อกับฐานข้อมูลจริงผ่าน `src/lib/supabase/live-store.ts` เรียบร้อย (`NEXT_PUBLIC_DATA_MODE=supabase` ใน `.env.local`) ส่วนด้านล่างนี้เก็บไว้เป็นคู่มืออ้างอิง เผื่อย้ายไปโปรเจกต์ Supabase ใหม่หรือรื้อจากศูนย์อีกครั้ง

1. **สร้างโปรเจกต์ Supabase** ที่ https://supabase.com/dashboard (ฟรีสำหรับเริ่มต้น)
2. เปิด **SQL Editor** แล้วรันตามลำดับ: `src/lib/supabase/schema.sql` → `src/lib/supabase/rls-policies.sql` → `src/lib/supabase/seed.sql`
3. ไปที่ **Project Settings > API** คัดลอก `Project URL` และ `anon public key`
4. สร้างไฟล์ `.env.local` จาก `.env.example` แล้วใส่ค่า:
   ```
   NEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=xxxx
   NEXT_PUBLIC_DATA_MODE=supabase
   ```
5. **ตั้งค่า Authentication:** เปิด Supabase Auth (Email/Password) แล้วสร้างผู้ใช้ให้พนักงานแต่ละคนใน Dashboard > Authentication > Users จากนั้นอัปเดต `employees.auth_user_id` ให้ตรงกับ `auth.users.id` ของแต่ละคน (รัน SQL `UPDATE employees SET auth_user_id = '...' WHERE id = '...';`) — ขั้นตอนนี้แทนที่ระบบ PIN แบบ prototype เมื่ออยู่ในโหมด `supabase`
6. **สร้าง Storage buckets** สำหรับรูปภาพ (`checklist-photos`, `milk-photos`, `purchase-photos`) — มี SQL ตัวอย่างอยู่ท้ายไฟล์ `rls-policies.sql` (คอมเมนต์ไว้ ให้เอาออกมารันได้เลย) — *หมายเหตุ: หน้าจอ UI ยังไม่ได้เรียก `uploadPhoto()` จริง รูปภาพยังเก็บเป็น data URL อยู่ (ดูหัวข้อ 13)*
7. **หน้าจอ UI ต่อฐานข้อมูลจริงให้อัตโนมัติแล้ว** ผ่าน `src/lib/supabase/live-store.ts` ซึ่งมี public API (`login`, `logout`, `submitChecklist`, `addMilkBatch` ฯลฯ) ตรงกับ mock store (`src/lib/store.ts`) ทุกตัว — `src/lib/store.ts` จะเลือกใช้ `LiveStore` (ฐานข้อมูลจริง) หรือ `Store` (mock/localStorage) โดยดูจาก `NEXT_PUBLIC_DATA_MODE` อัตโนมัติ ไม่ต้องแก้โค้ดหน้าจอเพิ่มเติม
8. รีสตาร์ท dev server (`npm run dev`) หลังแก้ `.env.local` ทุกครั้ง แล้วทดสอบล็อกอินด้วยอีเมล/รหัสผ่านของพนักงานที่สร้างไว้ในขั้นตอนที่ 5

## 9. ทำไมเลือก Supabase

- **PostgreSQL เต็มรูปแบบ** — ข้อมูลร้าน (สต๊อก, ล็อตนม, ประวัติ) เป็นข้อมูลเชิงสัมพันธ์ (relational) ชัดเจน เหมาะกับ SQL มากกว่า NoSQL แบบ Firestore
- **Row Level Security (RLS)** ตรงกับความต้องการ "3 ระดับสิทธิ์" ของสเปกนี้พอดี — เขียนกฎเป็น SQL policy ตรงไปตรงมา ไม่ต้องเขียน security rule ภาษาเฉพาะแบบ Firebase
- **Realtime subscriptions** ในตัว — ใช้ทำ Dashboard ที่อัปเดตสดได้โดยไม่ต้อง polling (เจ้าของร้านเปิดมือถือดูแล้วเห็นพนักงานทำเช็กลิสต์แบบ real-time)
- **Storage** สำหรับรูปภาพในตัว ไม่ต้องพึ่งบริการอื่นแยก
- **Edge Functions** ใช้ทำงานเบื้องหลัง เช่น cron ตรวจนมหมดอายุทุกชั่วโมงแล้วส่ง LINE/อีเมล
- ราคาระดับเริ่มต้นเหมาะกับร้านเบเกอรี่ขนาดเดียว ไม่ต้องเริ่มจ่ายแพงตั้งแต่วันแรก

## 10. แผนเชื่อม LINE Messaging API และอีเมล

ระบบเตรียมโครงไว้แล้วใน `.env.example` (`LINE_CHANNEL_ACCESS_TOKEN`, `LINE_CHANNEL_SECRET`, `LINE_NOTIFY_GROUP_ID`, `RESEND_API_KEY`) แนวทางที่แนะนำเมื่อจะทำจริง:

1. สร้าง **Supabase Edge Function** (หรือ Next.js API Route + cron ภายนอกเช่น Vercel Cron) ที่รันทุก 15–30 นาที
2. ให้ฟังก์ชันนี้ query สถานะปัจจุบัน (ใช้ตรรกะเดียวกับ `generateLiveNotifications()` ใน `src/lib/derive.ts` — ย้ายมา rewrite เป็น SQL/Edge Function เพื่อรันฝั่ง server)
3. เทียบกับ `notifications` ที่เคยส่งไปแล้ว (กันส่งซ้ำ) แล้วยิงข้อความผ่าน:
   - **LINE Messaging API**: `POST https://api.line.me/v2/bot/message/push` ไปยังกลุ่ม LINE ของร้าน (ใช้ `LINE_NOTIFY_GROUP_ID` + `LINE_CHANNEL_ACCESS_TOKEN`)
   - **อีเมล**: ผ่านผู้ให้บริการอย่าง Resend/SendGrid ส่งสรุปประจำวันให้เจ้าของร้าน
4. severity ระดับ "ห้ามใช้สินค้า" และ "เร่งด่วน" ควรส่งทันที ส่วน "ควรตรวจสอบ"/"ข้อมูลทั่วไป" อาจสรุปส่งวันละครั้ง (เช่น 20:00 น. สรุปวันนั้น) เพื่อไม่ให้พนักงาน/เจ้าของร้านเบื่อการแจ้งเตือน

## 11. Backup และ Audit Log

- **Audit Log = ตาราง `history_logs`** ที่มีอยู่แล้วในระบบ บันทึกทุกการกระทำสำคัญ (ทำเช็กลิสต์, ต้มนม, เปลี่ยนสถานะนม, ปรับสต๊อก, แจ้งของเสีย, สร้าง/อนุมัติ/รับคำสั่งซื้อ, เปลี่ยนการตั้งค่า) พร้อมระบุ **ใครทำ** และ **เมื่อไหร่** ทุกครั้ง ตรงตามสเปกข้อ 8 และ 14
- **Backup ฐานข้อมูล:**
  - Supabase มี **Point-in-Time Recovery (PITR)** และ backup รายวันอัตโนมัติในแผนเสียเงิน (Pro ขึ้นไป) — แนะนำเปิดใช้เมื่อขึ้นระบบจริง
  - เพิ่มเติมได้ด้วย **pg_dump ผ่าน GitHub Actions/cron รายวัน** ส่งไฟล์ .sql ไปเก็บที่ Supabase Storage bucket แยก หรือ S3/Google Drive เป็นชั้นสำรองที่สอง
  - เก็บ backup ย้อนหลังอย่างน้อย 30 วัน เพื่อรองรับการตรวจสอบย้อนหลังกรณีมีปัญหา

## 12. การป้องกันสิทธิ์และการแก้ไข/ลบประวัติ

- ตาราง `history_logs` มี RLS policy สำหรับ **INSERT และ SELECT เท่านั้น** — ไม่มี policy สำหรับ UPDATE/DELETE เลยแม้แต่ policy เดียว ผลคือ **ไม่มีผู้ใช้คนไหน (รวมถึง Owner) แก้ไขหรือลบแถวในตารางนี้ผ่าน client ได้** ต้องทำผ่าน service role key (เข้าถึงได้เฉพาะฝั่ง server/ผู้ดูแลระบบเท่านั้น) ซึ่งสอดคล้องกับสเปก "ห้ามลบประวัติสำคัญจากระบบโดยตรง"
- ตาราง `milk_batches` ไม่มี policy DELETE เช่นกัน (ห้ามลบล็อตนม สร้างใหม่ได้อย่างเดียว)
- การอนุมัติคำสั่งซื้อ (`purchase_requests` เปลี่ยนสถานะเป็น approved/ordered/received) จำกัดด้วย RLS ให้เฉพาะ role `owner`/`manager` เท่านั้น — พนักงาน (staff) แก้ไขได้เฉพาะรายการของตัวเองตอนยังอยู่สถานะ "รออนุมัติ" (เช่น แก้ไข/ยกเลิกก่อนมีคนอนุมัติ)
- การแก้ไขการตั้งค่าระบบ (`app_settings`) และสิทธิ์พนักงาน (`employees.role`) จำกัดเฉพาะ `owner`
- ทุก policy ใช้ฟังก์ชัน `current_employee_role()` ที่อ่านบทบาทจากตาราง `employees` โดยอิงจาก `auth.uid()` ของผู้ใช้ที่ล็อกอินอยู่จริง (ไม่ใช่ค่าที่ฝั่ง client ส่งมา) จึงปลอมแปลงสิทธิ์จาก browser ไม่ได้

## 13. ข้อจำกัดที่ทราบและสิ่งที่ควรทำต่อ

- **ยังไม่ได้รัน `npm install`/`npm run build` จริงในสภาพแวดล้อมที่แก้โค้ด wiring ล่าสุด** เนื่องจากสภาพแวดล้อมนั้นไม่มีอินเทอร์เน็ตออกไปยัง npm registry — ตรวจสอบไฟล์ทั้งหมดด้วยมือแล้ว (import ตรงกัน, type ตรงกัน, signature ของฟังก์ชันตรงกันระหว่าง `Store`/`LiveStore`/`AppStore`) แต่ **ควรรัน `npm run build` บนเครื่องจริงอีกครั้งเพื่อความมั่นใจ 100% ก่อนใช้งานจริง** และแจ้งกลับหากมี TypeScript error
- ระบบล็อกอินแบบ PIN เป็นของ prototype เท่านั้น ใช้เฉพาะตอน `NEXT_PUBLIC_DATA_MODE=mock` — ตอนนี้โปรเจกต์ตั้งเป็น `supabase` แล้วจึงใช้ Supabase Auth จริง (อีเมล+รหัสผ่าน) แทน
- `supabase/queries.ts` เขียนสมบูรณ์และผูกเข้ากับหน้า UI จริงแล้วผ่าน `supabase/live-store.ts` (ดูหัวข้อ 8)
- การคำนวณสถานะ (`derive.ts`) รันฝั่ง client เท่านั้นตอนนี้ — เมื่อขึ้นระบบจริงควร reproduce ตรรกะเดียวกันเป็น Postgres function/Edge Function เพื่อให้แจ้งเตือนทำงานได้แม้ไม่มีใครเปิดแอปอยู่
- ยังไม่มีการทดสอบอัตโนมัติ (unit/e2e tests) — แนะนำเพิ่ม Playwright สำหรับ flow หลัก (ล็อกอิน → ทำเช็กลิสต์ → ต้มนม → เสนอซื้อ → อนุมัติ) ก่อนขึ้นระบบจริง
- รายการเช็กลิสต์/รายชื่อวัตถุดิบในหน้า Settings ปัจจุบันเป็น read-only (ตามที่ระบุไว้ในหน้านั้น) — ต่อยอด CRUD เต็มรูปแบบได้จากตาราง `checklist_template_items`/`stock_items` ที่มีอยู่แล้ว
